# Muse 对接桥：省掉 pan 手动转发

目标：客户下单或在订单详情留言后，**不用 pan 转发**，Muse 就能直接按订单对接。
这不是实时聊天，是**异步订单留言**：客户在订单详情留言 → Muse 定时轮询 → 回复写回订单详情，客户在原订单里看到。

**顺序铁律（pan 2026-10-29 定）：收到先报 pan，再去处理，绝不先跟客户来回询盘半天才告诉 pan。**

## 对接全流程（pan 2026-10-29 定稿，18 步，顺序不可颠倒）

```
1.  客户发            客户下单，或在订单详情“对接留言”区留言
2.  你（Muse）        轮询发现（每 5 分钟），即按上一条把原单原话报给 pan：收到通知
3.  整理              Muse 把需求整理成正式需求单；缺项标“待确认”，不编价格与周期
4.  反馈客户          人话确认：按该单实际内容现写，像人说话。不含方案、报价、稿件
5.  反馈给我（pan）    把整理后的需求单发给 pan 过目
6.  我确认（pan）      pan 确认需求与方向
7.  你设计（Muse）     按确认后的方向出设计；无设计需求的标准品订单跳过 7–11 步
8.  反馈给我稿件       设计稿先发 pan，不先发客户
9.  我确认（pan）      pan 确认稿件
10. 给客户            经 pan 确认的稿件发给客户
11. 客户确认          客户确认稿件
12. 反馈确认信息给我  把客户的确认信息发给 pan
13. 确认下单（pan）    pan 确认可以下单
14. 客户付款          客户按既有支付流程付款
15. 最终下单          付款后订单锁定为最终单
16. 提交下单信息给我  Muse 把最终生产下单信息（规格、数量、材质等）提交给 pan
17. 到 QQ / 微信供应商下单
                      Muse 起草供应商下单文案，pan 用自己的 QQ / 微信发给供应商
                      （Muse 没有供应商 QQ / 微信直发通道，不代发）
18. 反馈客户已下单    pan 告知 Muse 已向供应商下单后，Muse 在订单详情回复客户：已下单
```

说明：
- 第 2 步与第 5 步都是报 pan，分工不同：第 2 步是“收到通知”（原单原话），
  第 5 步是“整理结果”（正式需求单）。两次都不等客户来回询盘。
- 第 4 步只能是人话确认，方案、报价、稿件一律走第 8–10 步：先 pan 确认，
  再给客户。这是第 4 步与先审后发不冲突的唯一读法；如 pan 另有定法，以 pan 为准。

## 给客户的回复：必须像人说话（pan 2026-10-29 定）

所有经 `museReply` 发给客户的文案（确认、追问、进度、已下单），一律按真人
设计师在微信里回话的语气写，不许发系统通知味的模板句。身份仍是 Muse
对接设计师，不冒充某个真人姓名；变的只是语气，不是身份。

- 说人话：用“你”，短句，第一人称“我”，提客户实际发的东西。
  不要“已收到您的需求，正在处理中”“对接设计师将稍后回复”这类第三人称模板句，
  不要“尊敬的客户”，不要每单都发同一句话。
- 一次只说一件事、只问一个关键问题，不要一次甩一串问题让客户填表。
- 每单现写：确认要带上该单的品类 / 数量 / 关键细节，让客户一看就知道这条
  是回他这单的，不是群发。
- 仍守规矩：不报价格、不提包月、不给电话邮箱、不单独承诺制作周期，
  方案与稿件只发 pan 确认过的版本；不确定的事直接问，不编。
- 不要连发轰炸：一次只发一条，客户没回就不追发；客户回了再按订单回。

反例（不许发）：
> 已收到，正在整理需求，稍后由对接设计师按订单回复。

正例（格式，供参考，品类数量须按真单写）：
> 收到啦，你这个发光字我先看一下，尺寸和安装位置我整理好再跟你对一遍，你先不用急。

- 客户在第 11 步之后如改需求，回到第 3 步重新整理，重新走确认链，不直接改单。

## 客户资料存档：百度网盘，只存设计文件与源文件（pan 2026-10-29 定）

- 存档位置（bypy 沙盒视角）：`正鑫越订单存档/<订单号>_<客户名称>-<下单日期>-<设计名称>/`
  下设 `设计文件/` 与 `源文件/`，订单文件夹根目录另有一份 `存档备注.txt`，
  首行即备注：客户名称-下单日期-设计名称，次行为订单号。根目录已于 2026-10-29
  在百度云建好并核对；备注格式已用测试单实测上传、核对、删除，存档现为空、无测试残留。
- 只存这两类文件加一份备注：最终确认版的设计文件与源文件。不存客户手机号、地址、
  付款信息、聊天记录、报价单与中间废弃稿；备注只写客户名称，不写电话地址；
  标准品无设计文件的订单不建存档。
- 存档时机（不改 18 步编号）：第 11 步客户确认稿件后存一次确认版；
  第 15 步最终下单后如文件有变，再更新一次存档。改需求重走流程时，
  以最新确认版为准。
- 工具：`muse-bridge/archive.py <订单号> <客户名称> <下单日期> <设计名称> <设计文件目录> <源文件目录>`，
  下单日期写 YYYY-MM-DD（YYYYMMDD 会自动转），上传后用 `bypy list` 核对回显。
  脚本只用本机已授权的 bypy（`~/workspace/.venv-bypy/bin/bypy`），不写任何密钥。
- API 约定（pan 2026-10-29 定）：现在这套用 bypy 现有授权就够，不问 pan 要 API；
  将来如需百度开放平台 API（超出 `/apps/bypy` 沙盒的全盘操作、分享链接等），
  到那一步停下，由 Muse 找 pan 要 API 凭证，绝不现编、绝不发聊天。
  注意：bypy 视角只是应用沙盒 `/apps/bypy`，不等同于网盘主页全部文件。

## 安全设计（缺一不可）

- 两道门：微信 HTTP API 的 access_token（须 AppSecret）+ payload 里的
  `MUSE_BRIDGE_SECRET`（云函数环境变量，与 Muse 侧环境变量同一值）。
  两道都对不上，一律只回“无权限”，不透露订单是否存在。
- musePoll 只回最小字段：订单号、类型、状态、需求摘要、商品明细、未读留言、
  对接回复。**不回 openid，不回客户手机号。** Muse 不需要手机号，回复走订单详情。
- museReply 只追加回复，不改订单状态与金额；报价仍走既有 submitQuote 流程，
  且须商家角色，Muse 侧不直接改价。
- 所有密钥只放云函数环境变量与 Muse 安全存储，**绝不进仓库、绝不发聊天**。
  本目录的 `bridge.py` 只从环境变量读密钥，`watermark.json` 只存时间水位。

## Muse 侧定时任务（部署后建）

每 5 分钟跑一次，任务内容固定为：跑 `python3 bridge.py poll` 取新单与未读留言，
然后按上面 18 步全流程推进本单，不跳步、不颠倒顺序：

1. 新单 / 新留言：立即报 pan（原单原话），再整理、再按单写一句人话确认给客户。
2. 整理后的需求单发 pan；pan 确认后才设计；稿件先发 pan，pan 确认后才给客户。
3. 客户确认信息发 pan；pan 确认下单、客户付款、最终下单后，Muse 提交最终
   生产下单信息给 pan；pan 用 QQ / 微信向供应商下单并告知 Muse 后，
   Muse 在订单详情回复客户已下单。
4. 实质回复、报价、方案、稿件，pan 未点头前一律不发客户；无新单新留言时静默。

注意：5 分钟是轮询能做到的最快常规节奏，不是秒级直推。秒级直推须由云函数
直接推到 pan 手机（短信或微信模板消息），那要另外申请短信签名 / 模板，
不在本批代码里；如需秒级，pan 另定，我再加。

## 上线前 pan 只需做一次（不是每单做）

1. 小程序正式 AppID 与云开发环境建好（当前仓库里仍是占位，须先替换）。
2. 微信开发者工具里部署云函数：新增 `musePoll`、`museReply`、`addOrderMessage`，
   改动 `createOrder`、`createCustomOrder`（其余云函数不动）。
3. 在云函数环境配置里设 `MUSE_BRIDGE_SECRET` 为一个随机长串，并把同一值
   交给 Muse 走安全存储（不发聊天）。
4. 把 AppSecret 交给 Muse 走安全存储（不发聊天），用于换 access_token。
5. 前端改动随小程序一起发布：订单详情“对接留言”区、对接设计师窗口文案。

没做完上面 5 步之前，桥是通不了的；做完之后，每单都不用 pan 转发。
